### PSC Engineering Requirements

**Think about the thing before how programmers usually write it.** Before inventing a type, method, interface, namespace or compiler operation, reason about the things involved as if no language or framework existed. What has identity, and what is a value? What is the thing, and what is only a representation of it? This is Magritte's *The Treachery of Images*, a painted pipe captioned "this is not a pipe": a handle is not what it identifies, `#FF8000` is not the colour, and a measurement is a picture of what happened. What belongs to the thing, and what exists only because of an environment? Move it to another environment (Windows to Android) and see which relationships survive. Find the counterexample that breaks the analogy, revise, and try another independent perspective. Then introduce only the machinery those relationships require: no `IWindow`, `WindowFactory` or `WindowManager` because other repositories have them. A name collision is a question about identity and representation before it is a reason for a namespace.

**Single-file architecture.** PSC is one self-contained PowerShell script exposing a stable, documented default API. It may grow as large as it needs to; a source tree or an assembly carrying its source are projections of that one script, never extra project files. Its implementation stays directly inspectable, without auxiliary source files, hidden compiler stages or external implementation languages.

**Professional implementation quality.** All PowerShell code must meet a standard suitable for rigorous review by experienced PowerShell and System.Management.Automation maintainers: idiomatic, semantically precise, structurally sound, and defensible in its correctness and its use of SMA. Expedient workarounds are not substitutes for correct engineering.

**SMA authors; the program declares its semantics.** SMA's parser, AST and binder supply authoring, source evidence and reference semantics. PSC reads SM source through SMA, and a construct SMA cannot parse and observe is not supported. PSC owns semantic definitions and binding; source AST ancestry and live CLR types are not semantic authority. SMA's run-time semantics were shaped for glue and are not a finished program's semantics. Each program PSC builds declares the semantics it is lowered to (for example: numbers that do not widen on overflow, no output-by-default pipeline, no dynamic binding, value types copied). PSC lowers them faithfully, keeps a stated list of where they differ from SMA, and covers each difference with a test. Where SMA lacks a form a native program needs, PSC levels SMA up instead of working around it.

**Type system sovereignty and interoperability.** PSC owns first-class typed representations of the ScriptType System (STS) and the Common Type System (CTS). STS supports independently acquired structural contracts, identity, composition, binding, refinement and realization; CTS preserves faithful CLI interoperability. Semantic analysis must not require runtime materialization. Mappings between STS and CTS are explicit, typed and reversible where representable. SMA is the authoring and source-evidence substrate. Managed CLI, NativeAOT and independent native ISA are supported realization paths; neither CLR nor the C runtime is intrinsic to STS. Independent native realization shall support explicit static, dynamic or absent C runtime linkage. Source, semantic and realization retention are explicit artifact requirements, independent of execution dependencies. Preserve NativeAOT for existing applications while developing independent native compilation. Reconcile and retire redundant type, binding and lowering machinery only after independent semantic and executable parity; do not disguise source or weaken tests to satisfy distribution checks. Treat Defender compatibility as an operational distribution requirement, submit suspected false positives for vendor review, and retain normal security protections.

**Types are declared, not rediscovered.** Every boundary carries its type: parameters, properties, and return types through `[OutputType()]`. Only locals are inferred. An untyped or `[object]` boundary is refused, not guessed at. PSC checks before it lowers, with the semantics TypeScript established: literal unions (`[ValidateSet()]`, enums), narrowing after `-is` and `$null` tests, `$null` only where `[AllowNull()]` or `Nullable` admits it, and switches over a closed set checked for exhaustiveness.

**Declaration forms.** PowerShell classes cannot yet declare value types, generic types, interfaces, property accessors, events or real visibility (`hidden` is display, not access). Each is added as a form SMA's parser sees, through keywords registered with `DynamicKeyword` (as PSC does for methods marked `[Keyword()]`) or attributes, and lowered to PSC-owned semantic definitions with tests for each supported realization, including faithful CLI metadata and CIL where applicable. Never rewrite source text or run a second parser.

**One namespace per program.** A program is one script, so its types share one namespace. Source may name it; when it does not, PSC names it for the program at compile (Notepad.exe in `Notepad`; PSC itself, compiled to one managed assembly, in `PSC`), so a compiled program does not collide with anything else. Today PSC emits into the global namespace; this is the target.

**Structural integrity.** Never substitute strings for structured language constructs, typed references, semantic identities or executable bindings. Compiled assemblies and IL are read as input; C# is never authored, compiled, generated or kept as truth. Do not use scriptblocks to bypass typed compilation, semantic analysis or source-level accountability. Never use regular expressions to parse, interpret or transform programming-language syntax when SMA's tokenizer, AST or semantic facilities can do it.

**Records are classes.** A record whose shape is known is a named class with a typed property for each field, initialized completely when its structure is known. Do not use `[pscustomobject]` or a hashtable as a record. Use `Add-Member` only when runtime extension of an existing object is semantically required. Do not restrict a representation merely because PSC has not implemented its lowering.

**Evidence.** An exact match is evidence only as far as its two sides are independent: runs that share hardware, inputs or a reference agree partly by construction, and integer results that never overflow agree across reorderings by arithmetic alone. Say what a comparison compared, and trust it once a deliberate one-bit perturbation shows it can fail. Use SMA's existing capabilities correctly and completely before extending them. Compiler limitations are established by executable tests, not assumed from the current implementation. Every extension stays structurally visible to SMA and carries tests demonstrating its behavior.

**Upstream acquisition.** Follow the integration roadmap embedded in PSC.ps1 and regenerated in README.md. Begin with actual PSC and donor declarations, tests and history. Pin revision, source identity, extent, license and evidence; disposition existing mechanisms before adding new ones. Use the retained graph's advisory redundancy analysis to investigate overlapping bodies and call evidence; shared spellings and identical tokens do not establish semantic equivalence or justify automatic retirement. Extract general mechanisms, not application architecture. Keep application semantics downstream. Reconcile types, identity, authority, lifetime and dependency boundaries; preserve Percept and use Propose/Proposal, Investigation, Observation, Assessment and Admission according to their distinct meanings. Prefer established NIST, CLR, ECMA-335 and ISA vocabulary where applicable. Original donor terms belong in provenance, not automatically in PSC's API.

**Acceptance and efficiency.** Specify criteria and independent comparison before implementation. Protect baseline checkers, runner, fixtures and their dependencies; changes to assessment authority require separate approval. Use typed source, structural editing, deterministic realization, negative controls, independent differential tests, full application regressions and scoped Conform. Measure comparable cold/warm execution, memory, artifact size and dependency closure; document tolerances, hardware, coverage and omissions. Do not count unsupported scope or unverified capability as completed. Prefer reuse and measured improvements over duplicate machinery. Candidate execution is trusted-source testing, not a sandbox.

**Publication and repository stewardship.** Commit cohesive verified increments to main with the expected parent; verify remote identities and report scope and any unavailable checks. Never overwrite another change or silently relax protected criteria. Regenerate README from PSC.ps1, maintain comments and objective state in the same change, and preserve historical results at their recorded revisions. When inspecting a donor, update its README with concrete findings, corrected commands or status and the relevant upstream objective (or record why no change is warranted). Fix bounded defects when practical; preserve downstream behavior and verify reconvergence before removing redundant implementations. Do not claim an acquisition has shipped merely because it appears in the roadmap.

**Self-hosting is a development workload, not a future cleanup.** Progressively lower PSC's own implementation and consume its compiled faculties in the active development session. The canonical PSC.ps1 is to be realizable as PSC.dll, PSC.exe, native executables, PSC.so/libpsc.so and PSC.apk on supported targets. Preserve one semantic implementation and API across realizations; do not develop independent compilers for each format. Use actual PSC, Pwsh, Notepad, PSNES and Kokoroku workloads to expose missing lowering and runtime capabilities. Improve the existing NativeAOT/ILC path concurrently with independent native AOT; neither CIL nor ILC is required for independent native compilation. Prefer direct ISA and native platform API emission, explicit ABI contracts, PSC-owned linking and no C runtime dependency; C/CRT linkage may be chosen explicitly where useful.

**SMA compatibility and SM activation.** Progressively lower the full semantics of SMA into CLR assemblies, including dynamic behavior; explicit SM semantic profiles are not grounds for abandoning broader SMA compatibility. SM1 (.sm1), Script Resource Module (.srm1) and Script Executable (.sexe) source use a PSC module import for their authoring and execution semantics in the authoring environment. This is distinct from ordinary PowerShell source; the resulting realization need not carry that authoring dependency. Use the SMA AST as source evidence, not as an executable substitute for lowering. Avoid executable ScriptBlockAst materialization and inlining patterns implicated in Defender detections; investigate actual causes with controlled experiments and normal security protections, not obfuscation or bypasses. Add-Type from C# source, generated C# and auxiliary C# implementations are forbidden.

**ScriptType, Vom and dynamic realization.** ScriptType is a first-class type system intended to assume the semantic responsibilities of CLR types, not a reflection wrapper. Acquire CLR assembly definitions and executable capabilities as an explicit compatibility target. Class definitions, instances, modules, bindings and realizations must support runtime creation and release; distinguish their lifetimes and identity. Vom is the mechanism for dynamic typing, dynamic classes, structural composition and dynamic invocation within statically compiled programs, as well as object relationships, identity and resource lifetime. Acquire revocable binding and dynamic-call mechanisms from Pwsh rather than routing dynamic execution through SMA or CLR reflection by default. Support in-memory module creation, composition, acquisition, release and reclamation, using CoreCLR 11 capabilities where appropriate to that realization. Account for outstanding references and active execution when releasing executable realizations. A longer-term acceptance workload is a CLR-free, dynamic Pwsh runspace lowered by PSC using STS and Vom. Investigate a Vom collector (VomC) for reclamation of unreachable graphs, cycles, class/module state and executable resources where needed; establish existing reclamation capabilities before adding a distinct collector. Use the names Vom and VomC, not all-capital initialisms.

**Informed, loud, graceful degradation.** Detect resource pressure, ambiguous or unsupported operations and partial failures early; retain typed observations and explicit coverage. Use Vom leasing, additional handles, bounded resource acquisition, revocation and reclamation to mitigate overload before exhaustion where safe. Do not treat the first localized refusal as the end of an investigation: continue independent admissible work, retain useful partial results, identify affected and unaffected scope, and report degradation explicitly with causes, impact and recovery options. Never silently substitute semantics, fabricate success, swallow failures or publish incomplete work as accepted. Fail closed where continuing would violate correctness, integrity, security or resource safety; a local refusal must not unnecessarily preclude diagnosis of the larger system. Test pressure, lease limits, exhaustion, cancellation, reclamation and recovery.

**Resident development and discovery.** Make PSC the primary instrument of its own development. Retain API, source revisions, ASTs, semantic definitions, referents, indexes and executable bindings; amortize acquisition and eliminate redundant parsing, traversal, reflection, measurement and script/process re-entry. Make expensive measurements demand-driven and queries genuinely resumable. Compile and use internal hot paths rather than repeatedly interpreting them. Structural query and editing must acquire full enclosing constructs, preserve revision identity, support grouped undo and determine dependency/impact scope; acquire Notepad's editing primitives and Pwsh's console, completion and presentation primitives without inheriting their application-specific architecture or scriptblock execution adapter. Expose discoverable operations through help and the same typed resident API for interactive and programmatic use. Replace routine grep/Git subprocess work with stronger PSC primitives where appropriate; preserve Git history and provenance at publication boundaries. Discovery, observation, inference, Percepts, counterexamples, proposals and refinement are intrinsic PSC mechanisms, not a separate Student or PSPerception component. Donor names belong in acquisition provenance, not PSC architecture or executable source vocabulary.

**Hardware-aware lowering and acquisition.** Inspect actual prior art in Pwsh, Kokoroku, Notepad, PSNES and other relevant repositories before implementing a mechanism. Acquire, reconcile and retire overlapping mechanisms after evidence of parity; do not copy whole architectures, reinvent established machinery or perpetuate band-aids and hot fixes. Use existing Pwsh ELF/COFF-related native, DEX, AXML, Deflate, APK, JNI and host work where applicable; acquire Kokoroku's typed ISA, packetization, memory scheduling and SIMD kernels. Treat AVX, AVX2, AVX-512, ARM SIMD and Hexagon HVX/HMX as first-class performance opportunities subject to target capability and explicit semantics. Compare against independent references and actual hardware; SDK kernels are baselines, not performance ceilings. Preserve scalar and supported-width behavior, precision and ABI correctness. Measure sustained workloads, not only synthetic microbenchmarks.

**Development discipline and continuity.** Test a claimed limitation with the actual available runtime, source or minimal executable experiment before accepting it; distinguish a current implementation refusal from an inherent limitation. Prefer eliminating work over instrumenting or caching redundant work. Keep focused edit-time verification inexpensive; run appropriate independent regression and Conform gates at publication rather than turning assurance into the primary development workload. Do not expand assessment machinery without a demonstrated requirement. Preserve the actual Git repository and object database, use normal clone/fetch/fast-forward where available, and keep the Drive workspace backup current after each publication. Never routinely fabricate comparison commits or silently substitute reconstructed history; explicitly report missing objects, network limitations and incomplete backup coverage. Recover from retained state and verify remote source identities before continuing.
