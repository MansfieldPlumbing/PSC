### PSC Engineering Requirements

**Single-file architecture.** PSC is one self-contained PowerShell script exposing a stable, documented default API. It may grow as large as it needs to; a source tree or an assembly carrying its source are projections of that one script, never extra project files. Its implementation stays directly inspectable, without auxiliary source files, hidden compiler stages or external implementation languages.

**Professional implementation quality.** All PowerShell code must meet a standard suitable for rigorous review by experienced PowerShell and System.Management.Automation maintainers: idiomatic, semantically precise, structurally sound, and defensible in its correctness and its use of SMA. Expedient workarounds are not substitutes for correct engineering.

**SMA authors; the program declares its semantics.** SMA's parser, AST and binder are where programs are written and analysed. PSC reads source only through them, and a construct SMA cannot parse and observe is not supported. SMA's run-time semantics were shaped for glue and are not a finished program's semantics. Each program PSC builds declares the semantics it is lowered to (for example: numbers that do not widen on overflow, no output-by-default pipeline, no dynamic binding, value types copied). PSC lowers them faithfully, keeps a stated list of where they differ from SMA, and covers each difference with a test. Where SMA lacks a form a native program needs, PSC levels SMA up instead of working around it.

**Types are declared, not rediscovered.** Every boundary carries its type: parameters, properties, and return types through `[OutputType()]`. Only locals are inferred. An untyped or `[object]` boundary is refused, not guessed at. PSC checks before it lowers, with the semantics TypeScript established: literal unions (`[ValidateSet()]`, enums), narrowing after `-is` and `$null` tests, `$null` only where `[AllowNull()]` or `Nullable` admits it, and switches over a closed set checked for exhaustiveness.

**Declaration forms.** PowerShell classes cannot yet declare value types, generic types, interfaces, property accessors, events or real visibility (`hidden` is display, not access). Each is added as a form SMA's parser sees, through keywords registered with `DynamicKeyword` (as PSC does for methods marked `[Keyword()]`) or attributes, and lowered to its IL equivalent with lowering tests. Never rewrite source text or run a second parser.

**One namespace per program.** A program is one script, so its types share one namespace. Source may name it; when it does not, PSC names it for the program at compile (Notepad.exe in `Notepad`; PSC itself, compiled to one managed assembly, in `PSC`), so a compiled program does not collide with anything else. Today PSC emits into the global namespace; this is the target.

**Structural integrity.** Never substitute strings for structured language constructs, typed references, semantic identities or executable bindings. Compiled assemblies and IL are read as input; C# is never authored, compiled, generated or kept as truth. Do not use scriptblocks to bypass typed compilation, semantic analysis or source-level accountability. Never use regular expressions to parse, interpret or transform programming-language syntax when SMA's tokenizer, AST or semantic facilities can do it.

**Records are classes.** A record whose shape is known is a named class with a typed property for each field, initialized completely when its structure is known. Do not use `[pscustomobject]` or a hashtable as a record. Use `Add-Member` only when runtime extension of an existing object is semantically required. Do not restrict a representation merely because PSC has not implemented its lowering.

**Evidence.** Use SMA's existing capabilities correctly and completely before extending them. Compiler limitations are established by executable tests, not assumed from the current implementation. Every extension stays structurally visible to SMA and carries tests demonstrating its behavior.
