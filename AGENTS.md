### PSC Engineering Requirements

**Single-file architecture.** PSC must be consolidated into one self-contained PowerShell script exposing a stable, documented default API. Its implementation must remain directly inspectable and maintainable without requiring auxiliary source files, hidden compiler stages, or external implementation languages.

**Professional implementation quality.** All PowerShell code must meet a standard suitable for rigorous review by experienced PowerShell and System.Management.Automation maintainers. Implementations must be idiomatic, semantically precise, structurally sound, and defensible against scrutiny of their correctness, use of SMA, and adherence to PowerShell's execution model. Expedient workarounds are not substitutes for correct engineering.

**SMA as the authority.** If SMA cannot observe, represent, and reason about a construct through its parser, AST, type system, and semantic machinery, the implementation is incomplete or incorrect. Extend SMA's capabilities where necessary rather than introducing parallel interpretations, opaque conventions, or mechanisms invisible to its analysis.

**Structural integrity.** Never substitute strings for structured language constructs, typed references, semantic identities, or executable bindings. Do not introduce C# source, C#-authored helper types, generated C# intermediates, or indirect mechanisms that conceal another language's implementation inside PowerShell. Do not use scriptblocks to bypass typed compilation, semantic analysis, or source-level accountability. Never use regular expressions to parse, interpret, or transform programming-language syntax when SMA's tokenizer, AST, or semantic facilities can perform the operation.

**Object semantics and representation.** Preserve PowerShell's Extended Type System as a first-class language capability. A record whose shape is known is a named class with a typed property for each field. Do not use `[pscustomobject]` or a hashtable as a record. Use `Add-Member` only when runtime extension of an existing object is semantically required. Initialize an object completely when its structure is already known. Do not impose representation restrictions merely because PSC has not implemented their lowering.

SMA must be able to observe and account for every supported construct through its syntax, binding, semantic analysis, or explicit runtime behavior. Absence from static completion is not proof of semantic invisibility. Where PSC specializes or replaces a PowerShell representation, establish behavioral equivalence through executable tests, including member access, mutation, type identity, and applicable ETS behavior. Optimize only where the transformation preserves the required semantics.

**Parsing is extended by mutating SMA's environment.** When the grammar needs a new construct, teach SMA's own parser before parsing (for example, keywords registered through `DynamicKeyword`, which PSC does for methods marked `[Keyword()]`), so the source parses to typed AST nodes. Never rewrite source text or run a second parser.

**Required engineering approach.** Use SMA's existing capabilities correctly and completely before extending them. When an existing capability is insufficient, identify the precise limitation and implement the necessary extension at the appropriate lexical, syntactic, binding, or semantic layer. Every extension must remain structurally visible to SMA, preserve explicit type and semantic information, and be supported by executable tests demonstrating the intended behavior. Compiler limitations must be established by evidence, not assumed from the current implementation.
