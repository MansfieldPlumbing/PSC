### PSC Engineering Requirements

**Think about the thing before how programmers usually write it.** Before inventing a type, method, interface, namespace or compiler operation, reason about the things involved as if no language or framework existed. What has identity, and what is a value? What is the thing, and what is only a representation of it? This is Magritte's *The Treachery of Images*, a painted pipe captioned "this is not a pipe": a handle is not what it identifies, `#FF8000` is not the colour, and a measurement is a picture of what happened. What belongs to the thing, and what exists only because of an environment? Move it to another environment (Windows to Android) and see which relationships survive. Find the counterexample that breaks the analogy, revise, and try another independent perspective. Then introduce only the machinery those relationships require: no `IWindow`, `WindowFactory` or `WindowManager` because other repositories have them. A name collision is a question about identity and representation before it is a reason for a namespace.

**Single-file architecture.** PSC is one self-contained PowerShell script exposing a stable, documented default API. Single-file distribution does not imply monolithic execution. Discovery and enumeration make PSC self-describing: enumerate its definitions, members, relationships, dependencies, operations, realizations and limitations through the same retained typed API used for development and execution. It may grow as large as it needs to; a source tree or an assembly carrying its source are projections of that one script, never extra project files. Its implementation stays directly inspectable, without auxiliary source files, hidden compiler stages or external implementation languages.

**Professional implementation quality.** All PowerShell code must meet a standard suitable for rigorous review by experienced PowerShell and System.Management.Automation maintainers: idiomatic, semantically precise, structurally sound, and defensible in its correctness and its use of SMA. Expedient workarounds are not substitutes for correct engineering.

**SMA authors; the program declares its semantics.** SMA's parser, AST and binder supply authoring, source evidence and reference semantics. PSC reads SM source through SMA, and a construct SMA cannot parse and observe is not supported. PSC owns semantic definitions and binding; source AST ancestry and live CLR types are not semantic authority. SMA's run-time semantics were shaped for glue and are not a finished program's semantics. Each program PSC builds declares the semantics it is lowered to (for example: numbers that do not widen on overflow, no output-by-default pipeline, no dynamic binding, value types copied). PSC lowers them faithfully, keeps a stated list of where they differ from SMA, and covers each difference with a test. Where SMA lacks a form a native program needs, PSC levels SMA up instead of working around it.

**Type system sovereignty and interoperability.** PSC owns first-class typed representations of the ScriptType System (STS) and the Common Type System (CTS). STS supports independently acquired structural contracts, identity, composition, binding, refinement and realization; CTS preserves faithful CLI interoperability. Semantic analysis must not require runtime materialization. Mappings between STS and CTS are explicit, typed and reversible where representable. SMA is the authoring and source-evidence substrate. Managed CLI, NativeAOT and independent native ISA are supported realization paths; neither CLR nor the C runtime is intrinsic to STS. Independent native realization shall support explicit static, dynamic or absent C runtime linkage. Source, semantic and realization retention are explicit artifact requirements, independent of execution dependencies. Preserve NativeAOT for existing applications while developing independent native compilation. Reconcile and retire redundant type, binding and lowering machinery only after independent semantic and executable parity; do not disguise source or weaken tests to satisfy distribution checks. Treat Defender compatibility as an operational distribution requirement, submit suspected false positives for vendor review, and retain normal security protections.

**Semantic authority and referents.** Acquire the complete visible declaration scope before choosing which declarations to realize. ScriptType owns definitions, type references, signatures, member and receiver semantics, inference, overload selection, conversions and compatibility. Discovery acquires and relates referents and exposes them through enumeration; a referent exists independently of its realization. HandleTable owns operational handles, leases and revocation, and HandleCollector owns eligible handle-backed reclamation. Bind names in their declared scope, then carry typed references and use handles only where operational lifetime or access requires them. A missing, unselected, revoked or unavailable realization does not erase a definition or authorize rebinding by spelling. Never substitute a loaded CLR type for a known STS referent, or use CLR reference equality, reflection or a CLR declaration projection as the semantic authority. CLR identity, metadata, reflection and layout are legitimate at explicit CTS acquisition, compatibility and realization boundaries. Keep semantic identity, realization identity and storage separate. PSC implementation source, including its bootstrap and verification modules, prohibits `$this` and implicit receiver binding. Express participants with explicit typed referents and ScriptType member semantics; replacing a spelling without replacing the implicit dependency does not qualify. Ordinary SMA input programs may use `$this`; bind that syntax through ScriptType for compatibility rather than adopting it in PSC itself.

**Types are declared, not rediscovered.** Every boundary carries its type: parameters, properties, and return types through `[OutputType()]`. Only locals are inferred. An untyped or `[object]` boundary is refused, not guessed at. PSC checks before it lowers, with the semantics TypeScript established: literal unions (`[ValidateSet()]`, enums), narrowing after `-is` and `$null` tests, `$null` only where `[AllowNull()]` or `Nullable` admits it, and switches over a closed set checked for exhaustiveness.

**Declaration forms.** PowerShell classes cannot yet declare value types, generic types, interfaces, property accessors, events or real visibility (`hidden` is display, not access). Each is added as a form SMA's parser sees, through keywords registered with `DynamicKeyword` (as PSC does for methods marked `[Keyword()]`) or attributes, and lowered to PSC-owned semantic definitions with tests for each supported realization, including faithful CLI metadata and CIL where applicable. Never rewrite source text or run a second parser.

**One namespace per program.** A program is one script, so its types share one namespace. Source may name it; when it does not, PSC names it for the program at compile (Notepad.exe in `Notepad`; PSC itself, compiled to one managed assembly, in `PSC`), so a compiled program does not collide with anything else. Today PSC emits into the global namespace; this is the target.

**Structural integrity.** Never substitute strings for structured language constructs, typed references, semantic identities or executable bindings. Compiled assemblies and IL are read as input; C# is never authored, compiled, generated or kept as truth. Do not use scriptblocks to bypass typed compilation, semantic analysis or source-level accountability. Never use regular expressions to parse, interpret or transform programming-language syntax when SMA's tokenizer, AST or semantic facilities can do it.

**Lower declarations, not reconstructed executable programs.** Consume original SMA AST referents and their enclosing semantic scope directly through the existing lowering path. Selection of declarations is a realization request, not construction of a new source program. Perform semantic transformations (including specialization and inlining) in PSC-owned bound representations, preserving source evidence and origin. Do not synthesize or execute SMA scriptblocks to discover types, recover members or perform ordinary compilation. Keep genuinely independent SMA reference execution in ordinary authored, inspectable and parameterized verification modules; preserve source fidelity and normal inspection, logging and application-control boundaries. Do not alter code, packaging or execution paths for the purpose of defeating security detection. A security finding must be investigated against actual behavior and documented guidance, not presumed benign or explained away by a successful build.

**Modules, not scriptblocks.** PSC is a durable composition of named modules contained by the canonical single file. Faculties, APIs, semantic operations and regression tests are modules with declared dependencies, explicit entry points, typed inputs and results; they do not require anonymous scriptblock expressions, executable `ScriptBlockAst` construction, `ScriptBlock` objects or `GetScriptBlock()` in PSC implementation source. Explicit authored references to those scriptblock types are migration violations, including nested signatures. Parser-owned roots and named declaration bodies remain source evidence; their occurrence inside SMA does not authorize execution or synthetic program construction. Do not hide executable source in strings or rename the same mechanism. Existing verification modules must be acquired, activated and invoked through the same module contract; preserve their independent test inputs and assertions. Ordinary SMA programs remain a compatibility input language, not a license to author PSC in its legacy execution model.

**Boot and durability.** Startup brings the declared modules online in dependency order: bounded acquisition/lowering seed, HandleTable, HandleCollector, ScriptType and Discovery, then their consumers, with explicit readiness, failures, identities, dependencies, realized entry points and retained state. Acquire Pwsh's actual Android startup and headless implementation before extending this machinery; at Pwsh revision 515a49aebd6c7494fd27f7a9d0459ecd4f247470, setup.ps1 declares session creation, command module admission and entry-point invocation (lines 2872–2966), and explicit headless/write-plan admission (lines 9312–9336). Use the same module lifecycle and typed API interactively or non-interactively, with explicit authorization of writes and no mandatory prompts, personal profile, console, repeated script execution or interactive-only initialization. Retain verified module definitions and realization identities across sessions where requested, invalidate on relevant source/dependency/target changes, and preserve an inspectable recovery path. A module that has failed activation is not online; dependent capabilities must fail visibly while independent work continues. Do not infer Defender safety from this architecture or alter it to evade detection; preserve normal inspection and protections.

**Records are classes.** A record whose shape is known is a named class with a typed property for each field, initialized completely when its structure is known. Do not use `[pscustomobject]` or a hashtable as a record. Use `Add-Member` only when runtime extension of an existing object is semantically required. Do not restrict a representation merely because PSC has not implemented its lowering.

**Evidence.** An exact match is evidence only as far as its two sides are independent: runs that share hardware, inputs or a reference agree partly by construction, and integer results that never overflow agree across reorderings by arithmetic alone. Say what a comparison compared, and trust it once a deliberate one-bit perturbation shows it can fail. Use SMA's existing capabilities correctly and completely before extending them. Compiler limitations are established by executable tests, not assumed from the current implementation. Every extension stays structurally visible to SMA and carries tests demonstrating its behavior.

**Upstream acquisition.** Reconcile the existing embedded integration roadmap into the single AGENTS.md campaign; remove completed work and retire the embedded roadmap and its planning-only machinery once actual surface and conformance checks are preserved. Do not maintain competing roadmaps. Begin with actual PSC and donor declarations, tests and history. Pin revision, source identity, extent, license and evidence; disposition existing mechanisms before adding new ones. Provenance is hashing: use existing source, dependency and artifact digests and Git object identities. Origin paths, revisions and derivation relationships remain ordinary source and Discovery evidence; do not introduce a separate provenance subsystem or equate identical bytes with semantic identity. Use the retained graph's advisory redundancy analysis to investigate overlapping bodies and call evidence; shared spellings and identical tokens do not establish semantic equivalence or justify automatic retirement. Extract general mechanisms, not application architecture. Keep application semantics downstream. Reconcile types, identity, authority, lifetime and dependency boundaries; preserve Percept and use Propose/Proposal, Investigation, Observation, Assessment and Admission according to their distinct meanings. Prefer established NIST, CLR, ECMA-335 and ISA vocabulary where applicable. Record original donor terms in acquisition records, not automatically in PSC's API.

**Acceptance and efficiency.** Specify criteria and independent comparison before implementation. Protect baseline verification operations, runner, verification modules and their dependencies; changes to assessment authority require separate approval. Binary identity baselines must identify the producing revision, target and verified toolchain manifest identities. Qualify comparisons against independently controlled prior-revision evidence; preserve historical digests and refuse unknown toolchains rather than accepting a candidate digest or skipping the comparison. Distinguish repeated managed emission from repeated native compilation and linking. Use typed source, structural editing, deterministic realization, negative controls, independent differential tests, full application regressions and scoped Conform. Measure comparable cold/warm execution, memory, artifact size and dependency closure; document tolerances, hardware, coverage and omissions. Do not count unsupported scope or unverified capability as completed. Prefer reuse and measured improvements over duplicate machinery. Candidate execution is trusted-source testing, not a sandbox.

**Architectural lint and Guard.** Lint must detect violations of the governing semantic and implementation boundaries, not merely conventional PowerShell style. Use structurally grounded evidence and explicit boundary classifications to identify late name-based type rediscovery, CLR identity or binding authority outside interoperability/realization, unnecessary executable AST materialization, undeclared or ambiguous receiver/member binding, untyped boundaries and redundant competing implementations. Distinguish a legitimate target adapter or bounded bootstrap from an unauthorized fallback. Findings must identify the referent, extent, governing rule and affected scope; do not infer semantic violations from a token alone. Test the rules with independent positive and negative cases. Use existing Guard admission with zero current findings. Every finding, including existing committed findings, verification findings, and findings in embedded test modules, fails admission; no grandfathering, thresholds or exemptions. Do not suppress findings to make a test green. Commit explicit failing migration checkpoints to main when needed to retain concrete progress; distinguish a checkpoint from accepted conformance and release quality. Continue independent tests and repairs without representing a failed Guard as successful. Changes to protected verification authority still require separate approval. Passing historical tests does not waive an architectural violation, and a proposed rule is not an implemented check.

**Publication and repository stewardship.** Commit cohesive increments to main with the expected parent; verify remote identities and report scope, actual failures and unavailable checks. During this strict migration, commit observed failures with the evidence and continue repair; a commit is not admission. Never overwrite another change or silently relax protected criteria. Regenerate README from PSC.ps1, maintain comments and objective state in the same change, and preserve historical results at their recorded revisions. When inspecting a donor, update its README with concrete findings, corrected commands or status and the relevant upstream objective (or record why no change is warranted). Fix bounded defects when practical; preserve downstream behavior and verify reconvergence before removing redundant implementations. Do not claim an acquisition has shipped merely because it appears in the roadmap.

**Self-hosting is a development workload, not a future cleanup.** Progressively lower PSC's own implementation and consume its compiled faculties in the active development session. The canonical PSC.ps1 is to be realizable as PSC.dll, PSC.exe, native executables, PSC.so/libpsc.so and PSC.apk on supported targets. Preserve one semantic implementation and API across realizations; do not develop independent compilers for each format. Use actual PSC, Pwsh, Notepad, PSNES and Kokoroku workloads to expose missing lowering and runtime capabilities. Improve the existing NativeAOT/ILC path concurrently with independent native AOT; neither CIL nor ILC is required for independent native compilation. Prefer direct ISA and native platform API emission, explicit ABI contracts, PSC-owned linking and no C runtime dependency; C/CRT linkage may be chosen explicitly where useful.

**Bootstrap and operational self-consumption.** Make lowering and activation of PSC's own HandleTable, HandleCollector, ScriptType and Discovery modules an early part of normal PSC startup, before ordinary semantic acquisition, binding, compilation or development operations. Use the existing lowering and faculty dependency machinery; bound and document the minimal seed required to lower those faculties, distinguish bootstrap-only execution from normal operation, and converge on one implementation. The authoring host may use SMA and CLR to acquire and bootstrap; that does not give them continuing authority over STS. Do not merely load assemblies alongside interpreted duplicates: ordinary operations must actually consume the activated faculties and retain their semantic identities. Do not silently fall back to an interpreted or CLR binder if activation or acquisition fails. Report the affected capability and continue independent admissible work. Verify cold startup, retained-session use, normal Compile/Query and the actual regression entry points, including distinct same-named definitions, missing realizations, handle revocation and stale references. A successful BuildRuntime, an isolated faculty test or a loaded DLL is not evidence of operational integration. Require executable evidence of the actual binding and dispatch paths before claiming self-hosting progress.

**Independent native realization as a semantic control.** Use a real native ISA/API helper, originating in PSC-owned declarations and bound operations, to expose CLR assumptions early. Its native execution must not require CLR, SMA, CIL, ILC or CRT; authoring and cross-compilation may still run in the existing host. Exercise existing ScriptType identity, member binding, storage, invocation and handle lifetime semantics in bounded increments, with independent executable positive and negative controls. Native layout, ABI, imports, register allocation and linking belong to realization, not the definition of a type. Before designing or extending a native emitter, inspect the actual machine emission and platform API implementations in Pwsh and Kokoroku, including their instruction encoders, fixups, object formats, ABI and platform bindings, and reconcile them with PSC's existing native encoding, IR and linker. Acquire proven mechanisms with pinned provenance and tests; do not build a second native binder, invent an alternate type system, or require a CLR projection or CIL producer on the independent path. Keep the established managed and NativeAOT paths working. An import-free binary produced from CLR-bound semantics proves execution independence only, not semantic independence.

**SMA compatibility and SM activation.** Progressively lower the full semantics of SMA into CLR assemblies, including dynamic behavior; explicit SM semantic profiles are not grounds for abandoning broader SMA compatibility. SM1 (.sm1), Script Resource Module (.srm1) and Script Executable (.sexe) source use a PSC module import for their authoring and execution semantics in the authoring environment. This is distinct from ordinary PowerShell source; the resulting realization need not carry that authoring dependency. Use the SMA AST as source evidence, not as an executable substitute for lowering. Avoid executable ScriptBlockAst materialization and inlining patterns implicated in Defender detections; investigate actual causes with controlled experiments and normal security protections, not obfuscation or bypasses. Add-Type from C# source, generated C# and auxiliary C# implementations are forbidden.

**ScriptType, handles and dynamic realization.** ScriptType is a first-class type system intended to assume the semantic responsibilities of CLR types, not a reflection wrapper. Acquire CLR assembly definitions and executable capabilities as an explicit compatibility target. Class definitions, instances, modules, bindings and realizations must support runtime creation and release; distinguish their lifetimes and identity. ScriptType defines dynamic typing, dynamic classes, structural composition and dynamic invocation within statically compiled programs. Discovery and enumeration expose their referents and relationships. HandleTable supplies operational access and lifetime where required; not every definition or object needs a handle. Acquire revocable binding and dynamic-call mechanisms from Pwsh rather than routing dynamic execution through SMA or CLR reflection by default. Support in-memory module creation, composition, acquisition, release and reclamation, using CoreCLR 11 capabilities where appropriate to that realization. Account for outstanding references and active execution when releasing executable realizations. A longer-term acceptance workload is a CLR-free, dynamic Pwsh runspace lowered by PSC using STS, Discovery and handle-backed lifetime where required. HandleTable owns withdrawal, eligibility and operational storage. HandleCollector owns deferred cleanup execution, completion and free-slot recycling, using the same table and synchronization boundary. The current synchronous lifetime contract realizes both classes in HandleTable.dll; do not claim independent activation or add a competing collector store. Future garbage collection and handle-backed reclamation development belongs to HandleCollector. Establish existing reclamation capabilities before extending to unreachable graphs or cycles; do not invent a tracing collector to justify a name.

**Informed, loud, graceful degradation.** Detect resource pressure, ambiguous or unsupported operations and partial failures early; retain typed observations and explicit coverage. Use HandleTable leasing, additional handles, bounded resource acquisition, revocation and reclamation to mitigate overload before exhaustion where safe. Do not treat the first localized refusal as the end of an investigation: continue independent admissible work, retain useful partial results, identify affected and unaffected scope, and report degradation explicitly with causes, impact and recovery options. Never silently substitute semantics, fabricate success, swallow failures or publish incomplete work as accepted. Fail closed where continuing would violate correctness, integrity, security or resource safety; a local refusal must not unnecessarily preclude diagnosis of the larger system. Test pressure, lease limits, exhaustion, cancellation, reclamation and recovery.

**Resident development and discovery.** Use PSC itself to edit PSC canonical source through revision-bound structural acquisition and grouped edits; no external source rewrite, bypass or competing editor. If the structural API cannot express an edit, expose that refusal and extend the API with evidence rather than silently editing around it. Verification operations and their dependencies are subject to the same rules; independently controlled prior revisions, negative controls and actual execution evidence remain necessary because self-assessment alone cannot establish trust. Make PSC the primary instrument of its own development. Retain API, source revisions, ASTs, semantic definitions, referents, indexes and executable bindings; amortize acquisition and eliminate redundant parsing, traversal, reflection, measurement and script/process re-entry. Make expensive measurements demand-driven and queries genuinely resumable. Compile and use internal hot paths rather than repeatedly interpreting them. Structural query and editing must acquire full enclosing constructs, preserve revision identity, support grouped undo and determine dependency/impact scope; acquire Notepad's editing primitives and Pwsh's console, completion and presentation primitives without inheriting their application-specific architecture or scriptblock execution adapter. Expose discoverable operations through help and the same typed resident API for interactive and programmatic use. Replace routine grep/Git subprocess work with stronger PSC primitives where appropriate; preserve Git history and provenance at publication boundaries. Discovery and enumeration are intrinsic PSC mechanisms for self-description, including observation, inference, Percepts, counterexamples, proposals and refinement, not a separate Student component. Acquire missing mechanisms from Kokoroku Student; do not acquire PSPerception or the failed Hunt implementation. Enumerate actual definitions, operations, relationships and evidence from retained state, exposing incomplete scope and ambiguity rather than maintaining a competing catalog. Reconcile the existing PscInvestigation and semantic graph with the retained source and ScriptType definitions before acquiring Student's missing relationship indexing, bounded investigation, capability composition and reconsideration behavior. DiscoveryMechanisms (formerly InquiryPrimitives) is not operational Discovery merely because it builds; at PSC.ps1 blob 82ae1b023c4f0007c2904e07be5193cca037d2c1 the former faculty declarations had no direct consumers outside their own module and faculty inventory. Verify published assembly consumers before retirement. Do not duplicate the graph or import donor CLR identity and reflection as semantic authority. Record donor names in acquisition records, not PSC architecture or executable source vocabulary.

**Hardware-aware lowering and acquisition.** Inspect actual prior art in Pwsh, Kokoroku, Notepad, PSNES and other relevant repositories before implementing a mechanism. Acquire, reconcile and retire overlapping mechanisms after evidence of parity; do not copy whole architectures, reinvent established machinery or perpetuate band-aids and hot fixes. Use existing Pwsh ELF/COFF-related native, DEX, AXML, Deflate, APK, JNI and host work where applicable; acquire Kokoroku's typed ISA, packetization, memory scheduling and SIMD kernels. Treat AVX, AVX2, AVX-512, ARM SIMD and Hexagon HVX/HMX as first-class performance opportunities subject to target capability and explicit semantics. Compare against independent references and actual hardware; SDK kernels are baselines, not performance ceilings. Preserve scalar and supported-width behavior, precision and ABI correctness. Measure sustained workloads, not only synthetic microbenchmarks.

**Reconcile before extending.** At the start of each development increment, recover the verified revision, read the relevant source comments and governing requirements, inspect the existing implementation and prior art, and identify the actual runtime path. Treat contradictions between comments, tests and behavior as defects to resolve, not new requirements to invent. Stop expanding a legacy mechanism when its intended replacement already exists; first establish and use the replacement in ordinary execution. Do not turn provisional compatibility code, a diagnostic workaround or a local compiler refusal into an architectural constraint. Preserve pending candidates and their evidence separately from accepted main. Keep the work focused on concrete operational integration, not repeated architectural restatement, redundant instrumentation or accumulating isolated green checks. Report what was actually changed, exercised and left unresolved.

**Development discipline and continuity.** Test a claimed limitation with the actual available runtime, source or minimal executable experiment before accepting it; distinguish a current implementation refusal from an inherent limitation. Prefer eliminating work over instrumenting or caching redundant work. Keep focused edit-time verification inexpensive; run appropriate independent regression and Conform gates at publication rather than turning assurance into the primary development workload. Do not expand assessment machinery without a demonstrated requirement. Preserve the actual Git repository and object database, use normal clone/fetch/fast-forward where available, and keep the Drive workspace backup current after each publication. Never routinely fabricate comparison commits or silently substitute reconstructed history; explicitly report missing objects, network limitations and incomplete backup coverage. Recover from retained state and verify remote source identities before continuing.
